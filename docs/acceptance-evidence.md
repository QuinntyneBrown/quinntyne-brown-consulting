## Current release checks

- `dotnet test backend/Qbc.Workboard.slnx --configuration Release`: 113 passed, 0 failed — 94 API acceptance tests and 19 CLI database-command tests. The nine added tests cover the time entry and the hours report. The CLI suite runs a real SQL Server database and is what proves the `AddTimeEntry` migration applies; the API suite builds its schema from the model and would pass without one.
- `dotnet test backend/tests/Qbc.Workboard.Api.IntegrationTests/...`: 94 passed with `ConnectionStrings__Workboard` pointed at an unroutable address, which is how the suite's independence from SQL Server is demonstrated rather than assumed. Repeat runs pass, so no test depends on another.
- `npm run test:e2e`: 137 passed, 0 failed in 2.1 minutes — every scenario in Chromium, read from the built bundle rather than the development server. The isolated suite starts neither .NET nor SQL Server; it was verified with no listener on the API port. `--repeat-each=2` passes 274, so no scenario depends on another.
- `npm run typecheck:e2e`: passed with the mock API, fixture, specifications, Page Objects, and Playwright configuration checked under the workspace's strict TypeScript rules.
- `dotnet publish backend/src/Qbc.Workboard.Api/Qbc.Workboard.Api.csproj --configuration Release --output artifacts/publish`: succeeded; a production smoke test returned HTTP 200 for the Angular `/board` fallback and the workspace API.
- Backend acceptance tests invoke the real ASP.NET Core controller, MediatR, validation, EF Core, and Problem Details path over an isolated in-process SQLite database. Each test builds its own application and its own database, so story keys start at `QBC-101` every time and no scenario can see another's records. The CLI suite keeps a real SQL Server database, because initializing and resetting one is the behaviour it exists to prove.
- Of the 183 Given/When/Then scenarios, 93 trace to backend behaviour and each has one integration test. The remaining 90 get none: 49 are UI-only, 20 describe the ATDD process, 8 are code organisation excluded by `L2-039`, 3 are backlog search and filtering the API does not implement, and the rest are form pre-selection, pointer drag, browser storage, a documentation statement, and criteria whose backend half a sibling scenario already covers.
- Browser specifications contain scenario intent only; selectors, navigation, interactions, and assertions are owned by Page Objects, while the auto fixture owns the shared API interception boundary.
- Every browser test receives fresh in-memory API state that survives reloads within the scenario, shaped by a named `seed` scenario where the Given clause needs it. Unhandled `/api` requests fail the test, and the suite starts neither .NET nor SQL Server. Tests run with a workspace session already held unless they opt into `locked`, so the passcode gate is exercised deliberately rather than incidentally.
- Of the 183 Given/When/Then scenarios in `docs/specs/L2.md`, 122 are observable through a browser against a mocked API. Each has at least one Playwright test; the `L2-047` and `L2-048` criteria describe the editor both an initiative and an epic are written on, so those are exercised once per record, which is why 137 tests cover 122 criteria. The remaining 61 get none: 40 describe code organisation or the ATDD process itself and are excluded by `L2-039`; 15 describe referential integrity, transactional rollback, Problem Details shape, credential issuance, passcode provisioning, or assembly-metadata version reads, which backend integration tests own; 2 describe a client calling the API directly past the frontend; 1 needs a backend restart; and 1 is a documentation requirement.
- The hours page was also walked against the running application and a real SQL Server database, through the real passcode gate: 19 of 19 checks, covering the directory's **Hours** action, the four totals, the completion share, the filter, the disclosed entries, logging two and a half hours, the confirmed deletion, the empty state, the `409` refusal of an assistant holding hours, and no horizontal overflow at 320, 390, 768, 1024, or 1440 CSS pixels. The walkthrough removed every record it created, so the workspace was left as it was found.
- Package restore/build output is warning-free, production dependencies have no reported npm audit findings, and production publish produces one ASP.NET-hosted application.
