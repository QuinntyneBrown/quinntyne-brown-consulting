# QBC Workboard — L2 Detailed Requirements

## 1. Conventions

- Every L2 requirement traces to exactly one requirement in `L1.md`.
- **GIVEN** describes preconditions, **WHEN** describes the user or system action, and **THEN** describes the observable result.
- IDs are server-generated, immutable, and unique. Story keys use the human-readable `QBC-{number}` format and are never reused.
- A sprint's 14-calendar-day range is inclusive: its end date is 13 calendar days after its start date.
- Story lifecycle (`Draft`, `Active`, or `Archived`), grooming readiness, sprint assignment, and board status are distinct concepts.
- Given/When/Then scenarios describing code organization or architecture remain acceptance criteria for review, but shall not be implemented as automated tests. ATDD automation applies only to executable product behavior and logic.

## 2. Workspace navigation

### L2-001 — Primary application routes

**Traces to:** L1-001

The application shall expose routes for the active board, backlog, initiative hierarchy, and assistant directory and shall provide persistent navigation among them.

#### Acceptance criteria

**Scenario: Navigate between work areas**

- **GIVEN** the application has loaded
- **WHEN** the user selects Board, Backlog, Initiatives, or Assistants
- **THEN** the corresponding view is displayed without a full-page browser reload
- **AND** the selected navigation item is visually identified
- **AND** the browser URL represents the selected route

**Scenario: Open a route directly**

- **GIVEN** the user has a valid deep link to a primary route
- **WHEN** the link is opened or refreshed
- **THEN** the requested view is displayed
- **AND** application state is loaded from the backend

**Scenario: Create a story from the global action**

- **GIVEN** the user is on any primary route
- **WHEN** the user invokes New story
- **THEN** the story creation experience opens without discarding the current route

## 3. Work hierarchy

### L2-002 — Initiative management

**Traces to:** L1-002

An initiative shall contain an ID, name, and outcome-oriented description. The description shall be markdown, and the application shall offer no other way to write it. The user shall be able to create, view, update, and delete initiatives.

#### Acceptance criteria

**Scenario: Create an initiative**

- **GIVEN** the user is viewing the initiative hierarchy
- **WHEN** the user starts an initiative, provides a non-blank name and description, and saves
- **THEN** the initiative is persisted
- **AND** it is displayed in the hierarchy

**Scenario: Author the description only as markdown**

- **GIVEN** the user is viewing the initiative hierarchy
- **WHEN** the user creates or updates an initiative
- **THEN** its description is written in the markdown document editor
- **AND** no plain-text description field is offered
- **AND** the hierarchy presents the description as prose rather than as markdown source

**Scenario: Reject an invalid initiative**

- **GIVEN** the initiative editor is open
- **WHEN** the user attempts to save with a blank name or description
- **THEN** the initiative is not persisted
- **AND** an error identifies every invalid field

**Scenario: Update an initiative**

- **GIVEN** an initiative exists
- **WHEN** the user changes its name or description and saves
- **THEN** the changes are persisted and shown wherever the initiative is referenced

**Scenario: Delete an empty initiative**

- **GIVEN** an initiative has no epics
- **WHEN** the user confirms its deletion
- **THEN** the initiative is permanently removed

**Scenario: Protect an initiative with epics**

- **GIVEN** an initiative has one or more epics
- **WHEN** the user attempts to delete it
- **THEN** deletion is rejected
- **AND** the user is told that the linked epics must first be moved or deleted

### L2-003 — Epic management

**Traces to:** L1-002

An epic shall contain an ID, name, summary, and one initiative reference. The summary shall be markdown, and the application shall offer no other way to write it. The user shall be able to create, view, update, move, and delete epics.

#### Acceptance criteria

**Scenario: Create an epic**

- **GIVEN** at least one initiative exists
- **WHEN** the user starts an epic, supplies a non-blank name and summary, selects an initiative, and saves
- **THEN** the epic is persisted beneath the selected initiative

**Scenario: Author the summary only as markdown**

- **GIVEN** the user is viewing the initiative hierarchy
- **WHEN** the user creates or updates an epic
- **THEN** its summary is written in the markdown document editor
- **AND** no plain-text summary field is offered
- **AND** the hierarchy presents the summary as prose rather than as markdown source

**Scenario: Reject an invalid epic**

- **GIVEN** the epic editor is open
- **WHEN** the user attempts to save with a blank name or summary
- **THEN** the epic is not persisted
- **AND** an error identifies every invalid field

**Scenario: Reject an oversized summary**

- **GIVEN** the epic editor is open
- **WHEN** the user saves a summary longer than the supported length
- **THEN** the epic is not persisted
- **AND** an error identifies the summary as too long

**Scenario: Update or move an epic**

- **GIVEN** an epic exists
- **WHEN** the user changes its name, summary, or parent initiative and saves
- **THEN** the changes are persisted
- **AND** the epic appears beneath its selected initiative
- **AND** its linked stories remain linked to the epic

**Scenario: Delete an empty epic**

- **GIVEN** an epic has no stories, including archived stories
- **WHEN** the user confirms its deletion
- **THEN** the epic is permanently removed

**Scenario: Protect an epic with stories**

- **GIVEN** an epic has at least one story
- **WHEN** the user attempts to delete it
- **THEN** deletion is rejected
- **AND** the user is told that its linked stories must first be moved or deleted

### L2-004 — Hierarchy presentation

**Traces to:** L1-002

The hierarchy view shall present initiatives with their epics and enough roll-up information to understand the work beneath them.

#### Acceptance criteria

**Scenario: View hierarchy roll-ups**

- **GIVEN** initiatives, epics, and stories exist
- **WHEN** the user opens the Initiatives view
- **THEN** each epic is displayed under exactly one initiative
- **AND** each initiative displays its epic and non-archived story counts
- **AND** each epic displays its non-archived story count and completion progress

**Scenario: Add nested work in context**

- **GIVEN** the hierarchy is displayed
- **WHEN** the user adds an epic from an initiative or a story from an epic
- **THEN** the parent is preselected on the surface that creates the record

## 4. Stories and tasks

### L2-005 — Story data and CRUD

**Traces to:** L1-003

A story shall contain an ID, story key, epic reference, title, description or user-story statement, acceptance criteria, story-point estimate, optional assistant owner, lifecycle state, readiness, optional sprint reference, board status, and zero or more tasks.

#### Acceptance criteria

**Scenario: Save a new draft**

- **GIVEN** at least one epic exists
- **WHEN** the user supplies a title and epic and creates a story
- **THEN** the backend assigns a unique story ID and sequential QBC story key
- **AND** the story is persisted in Draft state
- **AND** the story is not Ready

**Scenario: View a story**

- **GIVEN** a story exists
- **WHEN** the user opens it from the backlog, board, hierarchy, or an assistant assignment link
- **THEN** all story fields and tasks are available for review

**Scenario: Update a story**

- **GIVEN** a story exists and is not in a completed sprint
- **WHEN** the user changes valid editable fields and saves
- **THEN** the changes are persisted
- **AND** every view of the story reflects the changes

**Scenario: Validate story points**

- **GIVEN** the user is estimating a story
- **WHEN** an estimate is supplied
- **THEN** the accepted values are 1, 2, 3, 5, 8, or 13
- **AND** any other value is rejected by the backend and identified in the UI

### L2-006 — Story lifecycle and readiness

**Traces to:** L1-003

Story lifecycle states shall be Draft, Active, and Archived. Readiness shall be maintained independently for non-archived stories.

#### Acceptance criteria

**Scenario: Draft behavior**

- **GIVEN** a story is Draft
- **WHEN** it is displayed in the backlog
- **THEN** it is labeled Draft
- **AND** it cannot be assigned to a sprint

**Scenario: Mark a story Ready**

- **GIVEN** a Draft or Active story satisfies the grooming rules
- **WHEN** the user completes grooming
- **THEN** the story lifecycle becomes Active
- **AND** its readiness becomes Ready

**Scenario: Mark a story unready**

- **GIVEN** a Ready story is not assigned to a sprint
- **WHEN** the user marks it unready
- **THEN** its readiness becomes Not Ready
- **AND** it remains Active

**Scenario: Protect planned readiness**

- **GIVEN** a Ready story is assigned to a planned or active sprint
- **WHEN** the user attempts to mark it unready
- **THEN** the operation is rejected
- **AND** the user is told to remove the story from the sprint first

### L2-007 — Story task management

**Traces to:** L1-003

A story may contain checklist tasks. Each task shall contain an ID, non-blank title, completion state, and optional assistant assignee.

#### Acceptance criteria

**Scenario: Add a task**

- **GIVEN** the user is creating or editing a story
- **WHEN** the user enters a task title, optionally selects an assistant, and adds the task
- **THEN** the task is included when the story is saved
- **AND** it initially defaults to incomplete

**Scenario: Update a task**

- **GIVEN** a story contains a task
- **WHEN** the user changes its title, completion state, or assignee and saves the story
- **THEN** the task changes are persisted

**Scenario: Delete a task**

- **GIVEN** a story contains a task
- **WHEN** the user removes the task and saves the story
- **THEN** the task is permanently removed without deleting its parent story

**Scenario: Reject a blank task**

- **GIVEN** a story task is being added or edited
- **WHEN** its title is blank at save time
- **THEN** the save is rejected with a task-title validation message

### L2-008 — Story archive, restore, and deletion

**Traces to:** L1-003

The user shall be able to archive active work, restore archived work as a draft, and permanently delete a story after confirmation.

#### Acceptance criteria

**Scenario: Archive a story**

- **GIVEN** a non-archived story exists
- **WHEN** the user confirms Archive
- **THEN** the story becomes Archived and Not Ready
- **AND** any sprint assignment is removed
- **AND** its board status is reset to To do
- **AND** the story remains retrievable through the Archived backlog filter

**Scenario: Restore a story**

- **GIVEN** a story is Archived
- **WHEN** the user restores it
- **THEN** it becomes a Not Ready Draft in the backlog
- **AND** it has no sprint assignment

**Scenario: Permanently delete a story**

- **GIVEN** a story exists and is not retained in a completed sprint
- **WHEN** the user confirms permanent deletion
- **THEN** the story and its child tasks are permanently removed

**Scenario: Preserve sprint history**

- **GIVEN** a story is recorded as completed in a completed sprint
- **WHEN** the user attempts to archive or permanently delete it
- **THEN** the operation is rejected to preserve sprint history

## 5. Assistants and assignments

### L2-009 — Assistant directory and CRUD

**Traces to:** L1-004

An assistant shall contain an ID, full name, role, zero or more specialties, and an availability value of Available, Limited, or Unavailable.

#### Acceptance criteria

**Scenario: Create an assistant**

- **GIVEN** the user opens New assistant
- **WHEN** a non-blank full name and role and valid availability are saved
- **THEN** the assistant is persisted and displayed in the directory

**Scenario: View assistant workload**

- **GIVEN** an assistant owns stories or incomplete tasks
- **WHEN** the assistant directory is displayed
- **THEN** the assistant card shows counts for owned non-archived stories and incomplete assigned tasks

**Scenario: Update an assistant**

- **GIVEN** an assistant exists
- **WHEN** the user changes the assistant's name, role, specialties, or availability and saves
- **THEN** the changes are persisted and reflected on assignments

**Scenario: Delete an unassigned assistant**

- **GIVEN** an assistant has no story or task assignments
- **WHEN** the user confirms deletion
- **THEN** the assistant is permanently removed

### L2-010 — Story and task assignment

**Traces to:** L1-004

Each story and each task may be unassigned or assigned to one existing assistant.

#### Acceptance criteria

**Scenario: Assign an assistant**

- **GIVEN** at least one assistant exists
- **WHEN** the user selects an assistant as a story owner or task assignee and saves
- **THEN** the assignment is persisted
- **AND** the assistant's identity is visible with the work item

**Scenario: Unassign work**

- **GIVEN** a story or task has an assistant assignment
- **WHEN** the user selects Unassigned and saves
- **THEN** the assignment is removed without deleting either record

**Scenario: Protect an assigned assistant**

- **GIVEN** an assistant is assigned to one or more stories or tasks
- **WHEN** the user attempts to delete the assistant
- **THEN** deletion is rejected
- **AND** the UI lists every blocking story and task
- **AND** each listed assignment provides a way to open its story for reassignment

## 6. Backlog grooming

### L2-011 — Backlog presentation and discovery

**Traces to:** L1-005

The backlog shall show stories with their key, title, hierarchy context, lifecycle or readiness, estimate, and sprint disposition.

#### Acceptance criteria

**Scenario: View backlog context**

- **GIVEN** stories exist
- **WHEN** the user opens the backlog
- **THEN** each result displays its story key, title, initiative, epic, state or readiness, points, and current sprint disposition

**Scenario: Search stories**

- **GIVEN** the backlog is displayed
- **WHEN** the user searches by any portion of a story key, story title, or epic name without regard to letter case
- **THEN** only matching stories are displayed
- **AND** clearing the search restores the unfiltered result set

**Scenario: Filter stories**

- **GIVEN** the backlog contains stories in different states
- **WHEN** the user selects All, Unscheduled, Ready, Draft, or Archived
- **THEN** only stories matching the selected filter are displayed

**Scenario: Empty result**

- **GIVEN** no stories match the current search and filter
- **WHEN** the backlog result area is rendered
- **THEN** a clear empty state is shown
- **AND** the user can start creating a story from it

### L2-012 — Grooming validation

**Traces to:** L1-005

A story shall become Ready only when it has a title, valid epic, non-blank description or user story, non-blank acceptance criteria, and valid story-point estimate.

#### Acceptance criteria

**Scenario: Complete grooming**

- **GIVEN** a non-archived story contains every required grooming field
- **WHEN** the user marks the story Ready
- **THEN** the readiness change is persisted
- **AND** the story becomes eligible for sprint assignment

**Scenario: Reject incomplete grooming**

- **GIVEN** one or more grooming fields are missing or invalid
- **WHEN** the user attempts to mark the story Ready
- **THEN** the story remains Not Ready
- **AND** every missing or invalid grooming field is identified
- **AND** the user can immediately edit the story

**Scenario: Server-enforced readiness**

- **GIVEN** a client submits a readiness request directly to the API
- **WHEN** the story does not satisfy the grooming rules
- **THEN** the API rejects the request with validation details

## 7. Sprint planning

### L2-013 — Sprint CRUD and duration

**Traces to:** L1-006

A sprint shall contain an ID, unique name, non-blank goal, start date, derived end date, and status of Planned, Active, or Completed.

#### Acceptance criteria

**Scenario: Create a sprint**

- **GIVEN** the user is managing sprints
- **WHEN** the user supplies a unique name, goal, and valid start date and saves
- **THEN** a Planned sprint is persisted
- **AND** its end date is derived as 13 calendar days after its start date

**Scenario: Reject an invalid sprint**

- **GIVEN** the sprint form is open
- **WHEN** the user supplies a blank or duplicate name, blank goal, or invalid start date
- **THEN** the sprint is not persisted
- **AND** validation details identify the problem

**Scenario: Update a sprint**

- **GIVEN** a Planned or Active sprint exists
- **WHEN** the user changes valid sprint details and saves
- **THEN** the changes are persisted
- **AND** changing the start date recalculates the end date

**Scenario: Correct completed sprint metadata**

- **GIVEN** a Completed sprint exists
- **WHEN** the user corrects only its name or goal
- **THEN** the correction is persisted
- **AND** its dates, status, and completed story membership remain unchanged

### L2-014 — Sprint lifecycle

**Traces to:** L1-006

The system shall allow at most one Active sprint and shall enforce the Planned → Active → Completed lifecycle.

#### Acceptance criteria

**Scenario: Start a sprint**

- **GIVEN** a Planned sprint exists and no sprint is Active
- **WHEN** the user starts the sprint
- **THEN** its status becomes Active
- **AND** its assigned stories are available on the board

**Scenario: Reject a second active sprint**

- **GIVEN** one sprint is Active
- **WHEN** the user attempts to start another Planned sprint
- **THEN** the operation is rejected
- **AND** the current Active sprint remains unchanged

**Scenario: Complete an active sprint**

- **GIVEN** a sprint is Active
- **WHEN** the user confirms completion
- **THEN** the sprint becomes Completed
- **AND** no sprint is Active until a Planned sprint is explicitly started

**Scenario: Reject an invalid lifecycle transition**

- **GIVEN** a sprint is Planned or Completed
- **WHEN** the user attempts to complete it directly
- **THEN** the operation is rejected

### L2-015 — Sprint assignment

**Traces to:** L1-006

The user shall be able to assign eligible stories to a Planned or Active sprint and return eligible stories to the backlog.

#### Acceptance criteria

**Scenario: Plan a Ready story**

- **GIVEN** an Active, Ready, non-archived story is not retained in a Completed sprint
- **WHEN** the user assigns it to a Planned or Active sprint
- **THEN** the sprint assignment is persisted
- **AND** the story's board status is initialized to To do

**Scenario: Reject an ineligible story**

- **GIVEN** a story is Draft, Not Ready, Archived, or retained in a Completed sprint
- **WHEN** a sprint assignment is attempted
- **THEN** the operation is rejected without changing the story

**Scenario: Return planned work to the backlog**

- **GIVEN** a story belongs to a Planned or Active sprint
- **WHEN** the user removes its sprint assignment
- **THEN** the story returns to the unscheduled backlog
- **AND** its board status resets to To do

### L2-016 — Planned sprint deletion

**Traces to:** L1-006

Only a Planned sprint may be deleted.

#### Acceptance criteria

**Scenario: Delete a planned sprint**

- **GIVEN** a sprint is Planned
- **WHEN** the user confirms deletion
- **THEN** the sprint is permanently removed
- **AND** its assigned stories return to the backlog in To do status and remain Ready

**Scenario: Protect active and completed sprints**

- **GIVEN** a sprint is Active or Completed
- **WHEN** deletion is attempted through the UI or API
- **THEN** the operation is rejected
- **AND** sprint data and story membership remain unchanged

## 8. Sprint execution

### L2-017 — Active sprint summary

**Traces to:** L1-007

The board shall identify the Active sprint and summarize its goal, inclusive date range, story completion count, and completion percentage.

#### Acceptance criteria

**Scenario: Display the active sprint**

- **GIVEN** a sprint is Active
- **WHEN** the user opens the board
- **THEN** the sprint name, goal, start date, end date, completed-story count, total-story count, and completion percentage are displayed

**Scenario: Calculate progress**

- **GIVEN** an Active sprint contains stories
- **WHEN** board progress is calculated
- **THEN** the percentage equals Done stories divided by total sprint stories, rounded to a whole percentage

**Scenario: Display no-active-sprint state**

- **GIVEN** no sprint is Active
- **WHEN** the user opens the board
- **THEN** an empty state explains that no sprint is active
- **AND** it provides access to sprint management

### L2-018 — Board columns and story cards

**Traces to:** L1-007

The board shall have To do, In progress, and Done columns. Each sprint story shall appear in exactly one column.

#### Acceptance criteria

**Scenario: Render board stories**

- **GIVEN** an Active sprint contains stories in different board states
- **WHEN** the board is displayed
- **THEN** each non-archived sprint story appears once in its corresponding column
- **AND** each card displays its key, title, epic, estimate, owner, and task completion count when tasks exist
- **AND** each column displays its story count

**Scenario: Render an empty column**

- **GIVEN** a board column has no stories
- **WHEN** the board is displayed
- **THEN** the column remains visible with a zero count and clear empty state

### L2-019 — Board movement

**Traces to:** L1-007

The user shall be able to move an Active-sprint story among To do, In progress, and Done with controls that do not depend on drag-and-drop.

#### Acceptance criteria

**Scenario: Move a story with controls**

- **GIVEN** a story is on the Active sprint board
- **WHEN** the user moves it to another valid board state
- **THEN** the new state is persisted
- **AND** the card, column counts, and sprint progress update without a page reload

**Scenario: Move a story by dragging**

- **GIVEN** the user's device supports pointer drag-and-drop
- **WHEN** the story card is dropped on another valid board column
- **THEN** the same persisted movement behavior occurs

**Scenario: Reject movement outside the active sprint**

- **GIVEN** a story is not assigned to the Active sprint
- **WHEN** a board-state change is submitted to the API
- **THEN** the operation is rejected

### L2-020 — Sprint completion disposition

**Traces to:** L1-007

Completing a sprint shall preserve Done stories in sprint history and return unfinished stories to the Ready backlog.

#### Acceptance criteria

**Scenario: Complete a sprint with mixed work**

- **GIVEN** an Active sprint contains Done and unfinished stories
- **WHEN** the user confirms sprint completion
- **THEN** Done stories remain linked to the Completed sprint
- **AND** unfinished stories lose the sprint reference, retain Ready status, reset to To do, and appear as unscheduled backlog work

**Scenario: Review completed membership**

- **GIVEN** a sprint has been completed
- **WHEN** completed work is retrieved
- **THEN** its Done story membership remains available as historical data
- **AND** those stories cannot be assigned to another sprint

## 9. Data durability and integrity

### L2-021 — Server-side persistence

**Traces to:** L1-008

Initiatives, epics, stories, tasks, assistants, sprints, assignments, and lifecycle changes shall be stored by the backend in durable persistence.

#### Acceptance criteria

**Scenario: Persist across browser sessions**

- **GIVEN** a valid change has been confirmed by the API
- **WHEN** the browser is refreshed, closed and reopened, or used from another supported browser against the same backend
- **THEN** the persisted change is returned by the backend and rendered by the frontend

**Scenario: Persist across backend restart**

- **GIVEN** valid records have been saved
- **WHEN** the backend process restarts against the same configured data store
- **THEN** the records and relationships remain available

**Scenario: Avoid browser storage as the source of truth**

- **GIVEN** browser storage is empty or cleared
- **WHEN** the application session loads the workspace
- **THEN** persisted workspace data is restored from the backend

### L2-022 — Referential and transactional integrity

**Traces to:** L1-008

The backend shall enforce relationship and lifecycle rules atomically, regardless of which client invokes it.

#### Acceptance criteria

**Scenario: Reject an unknown parent or assignee**

- **GIVEN** a request references an initiative, epic, story, sprint, or assistant that does not exist
- **WHEN** the request is processed
- **THEN** the backend rejects it with an appropriate not-found or validation response
- **AND** no partial data is committed

**Scenario: Apply a multi-record transition atomically**

- **GIVEN** sprint completion or sprint deletion affects multiple stories
- **WHEN** any part of the operation fails
- **THEN** the entire operation is rolled back
- **AND** the sprint and all stories retain their prior state

**Scenario: Enforce deletion rules at the backend**

- **GIVEN** a client bypasses the frontend and requests a prohibited deletion
- **WHEN** the backend evaluates the request
- **THEN** the backend rejects the operation using the same rules exposed by the UI

### L2-023 — API validation and failure responses

**Traces to:** L1-008

The HTTP API shall validate all commands and return consistent machine-readable errors without exposing implementation details.

#### Acceptance criteria

**Scenario: Return validation details**

- **GIVEN** a request contains one or more invalid fields
- **WHEN** it reaches an API controller
- **THEN** the API returns HTTP 400 with RFC 9457 Problem Details
- **AND** field-specific errors are included when applicable

**Scenario: Return resource and conflict failures**

- **GIVEN** a requested resource is missing or a domain transition conflicts with current state
- **WHEN** the API processes the request
- **THEN** it returns HTTP 404 for a missing resource or HTTP 409 for a state conflict
- **AND** the response contains a stable problem type and human-readable detail

**Scenario: Protect internal information**

- **GIVEN** an unexpected server failure occurs
- **WHEN** an error response is produced outside development
- **THEN** the response does not include stack traces, secrets, database details, or internal file paths

## 10. Responsive and accessible experience

### L2-024 — Responsive layouts

**Traces to:** L1-009

All supported features shall remain usable without horizontal page scrolling at viewport widths from 320 CSS pixels upward.

#### Acceptance criteria

**Scenario: Use the product on a narrow viewport**

- **GIVEN** the viewport is between 320 and 759 CSS pixels wide
- **WHEN** any primary view or form is displayed
- **THEN** navigation is available through a compact menu
- **AND** data rows, cards, forms, actions, and board columns reflow into a readable single-column presentation
- **AND** no required content or action is clipped

**Scenario: Use the product on a wide viewport**

- **GIVEN** the viewport is at least 1000 CSS pixels wide
- **WHEN** the application is displayed
- **THEN** persistent navigation and a three-column sprint board use the available space
- **AND** line lengths and content widths remain readable

**Scenario: Use touch controls**

- **GIVEN** the product is used on a touch device
- **WHEN** the user operates navigation, forms, story movement, or dialogs
- **THEN** the workflow can be completed without hover or drag-and-drop

### L2-025 — Keyboard and assistive technology support

**Traces to:** L1-009

The application shall target WCAG 2.2 Level AA for the delivered workflows.

#### Acceptance criteria

**Scenario: Navigate by keyboard**

- **GIVEN** the user does not use a pointing device
- **WHEN** the user navigates with Tab, Shift+Tab, Enter, Space, arrow keys where semantically appropriate, and Escape
- **THEN** every interactive action is reachable and operable
- **AND** focus order is logical and focus is visibly indicated

**Scenario: Use a dialog**

- **GIVEN** a modal form or confirmation dialog opens
- **WHEN** keyboard or assistive technology is used
- **THEN** focus moves into the dialog and remains contained while it is open
- **AND** the dialog has an accessible name
- **AND** closing it returns focus to the invoking control when that control still exists

**Scenario: Interpret status without color**

- **GIVEN** lifecycle, readiness, availability, sprint status, or board status is displayed
- **WHEN** a user cannot distinguish the applied colors
- **THEN** visible text or another non-color cue communicates the status

**Scenario: Announce asynchronous feedback**

- **GIVEN** an operation completes or fails asynchronously
- **WHEN** feedback is presented
- **THEN** assistive technology is notified without unexpectedly moving keyboard focus

### L2-026 — Simple and forgiving interaction design

**Traces to:** L1-009

The product shall preserve the mock's restrained visual language, generous whitespace, clear typography, progressive disclosure, and explicit feedback.

#### Acceptance criteria

**Scenario: Confirm a destructive action**

- **GIVEN** the user initiates a permanent delete, archive, sprint completion, or another destructive operation
- **WHEN** confirmation is required
- **THEN** the dialog names the affected record and explains the consequence
- **AND** Cancel is available without changing data

**Scenario: Show operation state**

- **GIVEN** the frontend is waiting for an API operation
- **WHEN** the request is pending, succeeds, or fails
- **THEN** duplicate submission is prevented while pending
- **AND** success or actionable error feedback is displayed afterward

**Scenario: Show an empty collection**

- **GIVEN** a view or board column contains no records
- **WHEN** it is rendered
- **THEN** a purposeful empty state describes the condition
- **AND** a relevant next action is offered where one exists

## 11. Backend implementation

### L2-027 — Clean Architecture solution structure

**Traces to:** L1-010

The `backend/` folder shall contain a .NET solution separated into Domain, Application, Infrastructure, and API projects with dependencies pointing inward.

#### Acceptance criteria

**Scenario: Verify project dependencies**

- **GIVEN** the backend solution is restored
- **WHEN** project references are inspected

## 13. Product quality and delivery method

### L2-035 — Acceptance test-driven development workflow

**Traces to:** L1-012

Every change that implements or modifies executable product behavior or logic shall follow ATDD in a red–green–refactor sequence. Before production logic is written, the implementer shall select one corresponding Given/When/Then acceptance scenario and create either a backend integration test or a frontend Playwright end-to-end test that initially fails because the required behavior is absent or incorrect.

#### Acceptance criteria

**Scenario: Establish the acceptance boundary**

- **GIVEN** an implementer is about to add or change executable product behavior
- **WHEN** work on the vertical slice begins
- **THEN** the change is linked to at least one Given/When/Then scenario in this specification
- **AND** either a backend integration test or a frontend Playwright end-to-end test is selected as the acceptance boundary
- **AND** no production logic for that behavior is implemented before the acceptance test is written

**Scenario: Demonstrate the initial red state**

- **GIVEN** the acceptance test has been written and the required production behavior has not
- **WHEN** that test is run in isolation
- **THEN** it fails for the expected missing or incorrect behavior
- **AND** it does not fail because of test syntax, unavailable infrastructure, invalid test data, or an unrelated defect
- **AND** the work item or change record captures the test command, test name, and expected failure

**Scenario: Reach and retain the green state**

- **GIVEN** the expected failing acceptance test has been demonstrated
- **WHEN** production logic is implemented and the acceptance suite is run
- **THEN** the new acceptance test passes
- **AND** all previously passing acceptance tests remain green
- **AND** the new test stays in the regression suite

**Scenario: Change existing behavior**

- **GIVEN** existing behavior must be corrected or extended
- **WHEN** ATDD begins
- **THEN** a new or amended acceptance test first reproduces the unmet requirement as a failure
- **AND** the production change is made only after that failure is confirmed

**Scenario: Make a non-behavioral change**

- **GIVEN** a change affects only documentation, formatting, source organization, filenames, project structure, package metadata, or generated artifacts and does not alter executable behavior
- **WHEN** the change is implemented
- **THEN** an initial failing acceptance test is not required
- **AND** the applicable review, build, or static-analysis check is used instead

### L2-036 — Radically simple green implementation

**Traces to:** L1-012

After an acceptance test has demonstrated the expected failure, the implementation shall add the smallest coherent production change that satisfies the selected acceptance scenario. Speculative capabilities, unrelated refactoring, and abstractions not required by the current acceptance test are prohibited.

#### Acceptance criteria

**Scenario: Implement only what the acceptance test requires**

- **GIVEN** an acceptance test is red for the expected reason
- **WHEN** production code is added
- **THEN** the change implements only the behavior required to make that scenario pass
- **AND** it follows existing product and architecture patterns
- **AND** it does not add unrequested options, extension points, generalized frameworks, or unrelated features

**Scenario: Refactor after green**

- **GIVEN** the selected acceptance test and the existing suite are green
- **WHEN** the implementer improves names, removes duplication, or simplifies the implementation
- **THEN** observable behavior remains unchanged
- **AND** the complete affected acceptance suite remains green after each refactoring step

**Scenario: Reject a test-specific production shortcut**

- **GIVEN** the smallest implementation is being selected
- **WHEN** an implementation would hard-code test data, bypass a required layer, or behave correctly only in the test environment
- **THEN** that implementation is rejected
- **AND** the simplest implementation that satisfies the real acceptance boundary is used

### L2-037 — Backend integration acceptance tests

**Traces to:** L1-012

When a backend integration test is selected as the ATDD acceptance boundary, it shall exercise the behavior through the ASP.NET Core application boundary and include the controller, MediatR pipeline and handler, validation, and persistence behavior relevant to the scenario.

#### Acceptance criteria

**Scenario: Begin a backend behavior with a failing integration test**

- **GIVEN** a new or changed behavior is primarily enforced by the backend
- **WHEN** the implementer starts the change
- **THEN** an integration test invokes the application through its HTTP API or equivalent ASP.NET Core application host
- **AND** it initially fails for the expected unmet acceptance behavior
- **AND** mocked handler results are not used to bypass the controller-to-persistence path under test

**Scenario: Isolate persistent test data**

- **GIVEN** a backend integration test needs persistence
- **WHEN** the test runs
- **THEN** it uses an isolated test database or isolated database scope
- **AND** the test creates its own known data
- **AND** its result does not depend on test order or developer data

**Scenario: Cover backend product rules**

- **GIVEN** backend behavior for grooming, hierarchy protection, assistant protection, sprint assignment, sprint lifecycle, sprint completion, persistence, or API validation is implemented
- **WHEN** the backend acceptance suite runs
- **THEN** the corresponding rules are exercised through integration tests
- **AND** success and applicable validation, not-found, or conflict responses are verified

**Scenario: Use unit tests only as supporting tests**

- **GIVEN** a behavior has an initial failing integration or end-to-end acceptance test
- **WHEN** isolated domain logic would benefit from additional examples
- **THEN** focused unit tests may be added as supporting tests
- **AND** they do not replace the required initial acceptance test

### L2-038 — Frontend Playwright acceptance tests

**Traces to:** L1-012

When a frontend end-to-end test is selected as the ATDD acceptance boundary, it shall use Playwright against the running Angular application and an isolated, stateful mock of the public API contract. All Playwright tests shall use the Page Object Model. Backend behavior shall remain covered by backend integration tests through the real ASP.NET Core and persistence boundaries.

#### Acceptance criteria

**Scenario: Begin a user-visible behavior with a failing end-to-end test**

- **GIVEN** a new or changed behavior is observable through the web application
- **WHEN** the implementer starts the change with a frontend acceptance test
- **THEN** a Playwright test expresses the selected Given/When/Then scenario through the rendered UI
- **AND** it initially fails for the expected unmet behavior
- **AND** it runs against the application through its public browser and HTTP contract boundaries

**Scenario: Enforce the Page Object Model**

- **GIVEN** a Playwright specification interacts with the application
- **WHEN** the test source is inspected
- **THEN** page objects own selectors, element locators, navigation, UI actions, and reusable assertions
- **AND** the specification expresses scenario intent through page-object methods
- **AND** the specification does not use raw page locators, CSS or XPath selectors, or direct `page.evaluate` calls

**Scenario: Keep page objects behavior-focused**

- **GIVEN** a page object supports a workflow
- **WHEN** it is implemented
- **THEN** its methods describe user-recognizable actions or observations
- **AND** it does not expose DOM implementation details to test specifications

**Scenario: Isolate the browser acceptance environment**

- **GIVEN** the Playwright suite starts a test
- **WHEN** the Angular application issues requests to `/api`
- **THEN** a fresh stateful mock handles the request without a running backend process or test database
- **AND** state changes remain observable after browser reloads within that test
- **AND** state is reset before the next test
- **AND** any API request without an explicit mock handler fails the test

**Scenario: Exercise critical product workflows**

- **GIVEN** the Angular frontend and mocked API test environment is running
- **WHEN** the Playwright acceptance suite executes
- **THEN** it covers initiative and epic creation, draft-story grooming, task and assistant assignment, sprint planning, board movement, sprint completion, archive and restore, guarded deletion, persistence after reload, and API failure feedback
- **AND** the tests pass without relying on execution order or pre-existing developer data

**Scenario: Use component tests only as supporting tests**

- **GIVEN** a behavior has an initial failing integration or end-to-end acceptance test
- **WHEN** isolated Signal or component logic would benefit from additional examples
- **THEN** focused unit or component tests may be added as supporting tests
- **AND** they do not replace the required initial acceptance test

### L2-039 — Exclusion of code-organization tests

**Traces to:** L1-012

Automated acceptance, integration, end-to-end, unit, or component tests shall verify executable behavior and logic only. Tests whose purpose is to police code organization or other non-behavioral implementation constraints shall not be created.

#### Acceptance criteria

**Scenario: Verify architecture without behavioral tests**

- **GIVEN** folder placement, Clean Architecture dependency direction, controller usage, file-per-type rules, Angular external-file conventions, Signals usage, service-contract imports, or package-version requirements must be verified
- **WHEN** implementation compliance is evaluated
- **THEN** code review and ordinary compiler, build, package, or static-analysis output are used
- **AND** no automated product test is added solely to inspect source files, paths, imports, declarations, or project references

**Scenario: Retain tests that verify observable logic**

- **GIVEN** a test happens to cross multiple architectural layers
- **WHEN** its purpose is evaluated
- **THEN** it remains valid when it verifies observable product behavior or logic
- **AND** it is not rejected merely because the tested implementation follows an architectural structure

### L2-040 — Responsive and accessibility verification

**Traces to:** L1-012

Automated and manual release checks shall verify the supported responsive and accessibility behaviors. These checks shall exercise rendered user behavior rather than source-code organization.

#### Acceptance criteria

**Scenario: Verify representative viewports**

- **GIVEN** the release candidate is running
- **WHEN** critical workflows are tested at 320, 390, 768, 1024, and 1440 CSS-pixel viewport widths
- **THEN** no required content or action is clipped
- **AND** workflows complete without horizontal page scrolling

**Scenario: Verify accessibility**

- **GIVEN** the release candidate is running

- **THEN** no critical or serious automated violation remains
- **AND** keyboard operation, focus management, accessible names, status announcements, and non-color cues satisfy L2-025

## 14. Workspace access

### L2-041 — Shared passcode gate

**Traces to:** L1-013

Every `/api` work-management resource shall require a valid workspace session credential. The backend shall issue that credential only in exchange for the shared passcode, shall store the passcode as a salted hash rather than a recoverable value, and shall create the passcode record on every database initialization and reset so a usable workspace is never left without one.

#### Acceptance criteria

**Scenario: Open the workspace with the passcode**

- **GIVEN** the workspace passcode record exists
- **WHEN** the correct passcode is presented to the unlock resource
- **THEN** the API returns a signed session credential and the moment it expires
- **AND** that credential authorizes subsequent work-management requests

**Scenario: Refuse an incorrect passcode**

- **GIVEN** the workspace passcode record exists
- **WHEN** an incorrect passcode is presented
- **THEN** the API returns HTTP 401 with RFC 9457 Problem Details
- **AND** the response does not reveal the expected passcode or distinguish a wrong passcode from a missing record

**Scenario: Refuse an unaccompanied request**

- **GIVEN** a request carries no session credential or an expired one
- **WHEN** it reaches any work-management resource
- **THEN** the API returns HTTP 401 with RFC 9457 Problem Details
- **AND** no work-management data is read or changed

**Scenario: Provision the passcode with the database**

- **GIVEN** an operator initializes or resets the database, with or without representative data
- **WHEN** the operation completes
- **THEN** exactly one passcode record exists
- **AND** it carries a hashed passcode and a signing key that were not committed to source control

### L2-042 — Passcode attempt throttling

**Traces to:** L1-013

The unlock resource shall limit how many passcode attempts one caller may make in a fixed window and shall reject further attempts in that window without evaluating the passcode.

#### Acceptance criteria

**Scenario: Throttle repeated attempts**

- **GIVEN** a caller has exhausted the permitted attempts within the window
- **WHEN** the caller presents another passcode
- **THEN** the API returns HTTP 429 with RFC 9457 Problem Details
- **AND** the response states that attempts may resume later without naming the remaining count

**Scenario: Keep the gate honest about its strength**

- **GIVEN** the passcode is a short shared secret rather than a per-person credential
- **WHEN** the product documents the gate
- **THEN** the documentation states that throttling, not passcode length, is what makes guessing impractical

### L2-043 — Unlock experience

**Traces to:** L1-013

The Angular application shall present a full-page passcode screen outside the workspace chrome, shall send the visitor there whenever no valid session credential is held, and shall return to the board after a brief confirmation once the passcode is accepted.

#### Acceptance criteria

**Scenario: Send a locked visitor to the passcode screen**

- **GIVEN** the browser holds no valid session credential
- **WHEN** any workspace route is opened
- **THEN** the passcode screen is displayed without the sidebar, topbar, or breadcrumb
- **AND** no work-management request is issued

**Scenario: Enter the passcode**

- **GIVEN** the passcode screen is displayed
- **WHEN** the visitor enters the complete passcode
- **THEN** the passcode is submitted without a further action
- **AND** a confirmation is shown briefly before the board is displayed

**Scenario: Report a refused passcode**

- **GIVEN** the passcode screen is displayed
- **WHEN** an incorrect passcode is entered
- **THEN** the server's message is announced to assistive technology
- **AND** the field is cleared and returned to focus for another attempt

**Scenario: Return to the passcode screen when a session ends**

- **GIVEN** the workspace is open and the held credential is rejected by the server
- **WHEN** the rejection is received
- **THEN** the stored credential is discarded
- **AND** the passcode screen is displayed

- **THEN** the record is persisted
- **AND** the navigation completes

**Scenario: Save and continue from a new record**

- **GIVEN** a record that has never been saved holds unsaved changes
- **WHEN** the user chooses to save and continue
- **THEN** the record is persisted
- **AND** the navigation the user asked for completes

**Scenario: Keep the document out of browser storage**

- **GIVEN** a document holds unsaved changes
- **WHEN** browser storage is inspected
- **THEN** it holds only the workspace session credential

### L2-049 — Epic summary editor

**Traces to:** L1-002

An epic's summary shall be authored and read as a markdown document on its own addressable route. The same route shall create an epic and edit an existing one. The application shall present the parent initiative, the name, and the summary for one epic, shall save them together, and shall preserve the summary's markdown structure. A summary shall remain required, and the API shall reject a summary longer than the supported length.

#### Acceptance criteria

**Scenario: Open an epic and its summary**

- **GIVEN** an epic exists
- **WHEN** the user opens it from the initiative hierarchy
- **THEN** the epic's parent, name, and markdown summary are displayed together
- **AND** the browser URL identifies the epic that is open
- **AND** opening that URL directly displays the same epic

**Scenario: Create an epic from the editor**

- **GIVEN** the user is viewing the initiative hierarchy
- **WHEN** the user starts an epic from an initiative and saves a non-blank name and summary
- **THEN** the epic is persisted beneath that initiative
- **AND** the browser URL then identifies the epic that was created
- **AND** the editor reports the epic as saved

**Scenario: Save an edited summary**

- **GIVEN** an epic is open in the editor
- **WHEN** the user changes the name, the parent, or the markdown and saves
- **THEN** the changes are persisted
- **AND** they are shown wherever the epic is referenced

**Scenario: Preserve markdown structure**

- **GIVEN** a summary containing headings, nested lists, and emphasis
- **WHEN** it is saved and read again
- **THEN** every line of the markdown is returned as it was written
- **AND** only whitespace leading and trailing the whole document is removed

**Scenario: Reject a blank summary**

- **GIVEN** an epic is open in the editor
- **WHEN** the user clears the name or the summary and saves
- **THEN** the epic is not persisted
- **AND** an error identifies every invalid field

## 17. Logged hours

### L2-050 — Time entry data and logging

**Traces to:** L1-015

A time entry shall contain an ID, the story the time was spent on, the assistant it is attributed to, the date worked, a positive number of hours in quarter-hour increments no greater than 24, and an optional note.

#### Acceptance criteria

**Scenario: Log hours against a story**

- **GIVEN** a story and an assistant exist
- **WHEN** the user records a date, an amount of hours, and an optional note against them
- **THEN** the entry is persisted and attributed to the chosen assistant
- **AND** the recorded hours are included in that assistant's totals

**Scenario: Reject an invalid entry**

- **GIVEN** the user is recording time
- **WHEN** the hours are zero, negative, greater than 24, or not a quarter-hour increment, or the date is absent
- **THEN** the entry is not persisted
- **AND** an error identifies every invalid field

**Scenario: Reject an entry against an unknown story or assistant**

- **GIVEN** a story ID or assistant ID that names no record
- **WHEN** an entry is recorded against it
- **THEN** the entry is not persisted
- **AND** the response identifies the missing record

**Scenario: Amend an entry**

- **GIVEN** an entry has been recorded
- **WHEN** the user corrects the story, the date, the hours, or the note and saves
- **THEN** the entry is restated in place, keeping its identity
- **AND** the assistant's totals report the corrected hours rather than both readings

**Scenario: Reject an invalid amendment**

- **GIVEN** the user is correcting a recorded entry
- **WHEN** the corrected hours or date are invalid, or the entry or the story named no longer exists
- **THEN** the correction is not persisted
- **AND** the original entry is left as it was recorded

**Scenario: Delete an entry**

- **GIVEN** an entry has been recorded
- **WHEN** the user confirms its deletion
- **THEN** the entry is permanently removed
- **AND** the assistant's totals no longer include its hours

**Scenario: Protect an assistant with logged hours**

- **GIVEN** an assistant has hours logged against one or more stories
- **WHEN** the user attempts to delete the assistant
- **THEN** deletion is rejected
- **AND** the response lists every story holding that assistant's hours

### L2-051 — Assistant hours page

**Traces to:** L1-015

The workspace shall provide, for a single assistant, a page reporting the hours they logged, how much of that time is on stories that are now complete, and every story they worked on, where an assistant has worked on a story when they have hours logged against it.

#### Acceptance criteria

**Scenario: Open an assistant's hours**

- **GIVEN** an assistant with logged hours is listed in the directory
- **WHEN** the user opens that assistant's hours
- **THEN** the page identifies the assistant
- **AND** it reports the total hours logged, the hours on completed stories, the number of stories worked on, and how many of those are complete

**Scenario: Trace hours to completed stories**

- **GIVEN** an assistant has logged hours against both completed and in-flight stories
- **WHEN** the page is displayed
- **THEN** the share of logged hours that is on completed stories is reported as a proportion of the total
- **AND** the hours on completed stories never exceed the total hours logged

**Scenario: Filter to completed or in-flight work**

- **GIVEN** the page lists stories in both states
- **WHEN** the user selects Completed or In flight
- **THEN** only the stories in that state are listed
- **AND** the reported totals are unchanged, because they describe all logged time

**Scenario: Read the entries behind a story**

- **GIVEN** a listed story carries more than one entry
- **WHEN** the user expands that story
- **THEN** each entry is shown with its date, hours, and note
- **AND** the story reports the assistant's own hours separately from every hour logged against it

**Scenario: Guide an assistant with no logged hours**

- **GIVEN** an assistant has no time entries
- **WHEN** their hours page is displayed
- **THEN** the page explains that no hours are logged yet and offers to log the first
- **AND** no proportion is reported, because there are no hours to divide
